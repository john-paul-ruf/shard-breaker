## Architecture Reference (feature-specific only; full config in PROGRAM-CONFIG)

The functional core / imperative shell is built and verified. `AppStore` serializes commands, injects `commitId`/`now`, invokes the pure `runReducer`, and delegates atomic writes to `RunLifecycleRepository.saveCheckpoint`. Committed generators: `generateRouteOptions`, `generateRoomCandidate`, `generateShopInventory`, `generateThreatProfile`, `generateRewardDraft` (S01). The run lifecycle handles `StartRun`, `AbandonRun`, `MaterializeRoute`, `SelectRouteOffer`, `CommitRoute`. After `CommitRoute`, the living run is in `phase: "room"` with a populated `roomState` (status `"ready"`, `combatCheckpoint: null`). Navigation returns `home/checkpoint` for room/reward-phase runs — there is no room or reward screen yet.

This feature adds: room resolution commands (`BuyShopItem`, `CommitRecovery`, `ResolveRoom`, `SelectReward`) + store handlers (S02); a `RoomScreen` (room-type-specific interactions), a `RewardsScreen` (3-card draft), a `RewardCard` component, navigation for room/reward phases, styles, and browser e2e proofs (S03). Combat rooms (battle/elite/boss) show a "combat engine coming soon" placeholder and cannot be resolved — the combat engine (M04/M06) is the next feature.

## Design Decisions (choice + rationale)

1. **Reward content was created in the prior S01** — committed, tested, producer-ready. No Author handoff covers authored data tables; counts match the requirements constraints (8 skills, 8 equipment, 14 enhancements).
2. **Combat rooms cannot be resolved in this feature.** The combat domain (M04) and game bridge (M06) do not exist — `src/domain/combat/` and `src/game/` are absent. `ResolveRoom` rejects battle/elite/boss with `combat-not-implemented`; the RoomScreen shows a placeholder with a disabled resolve action. Building the fixed-step physics simulation, Canvas renderer, pointer input, collision detection, and boss phases is the next feature.
3. **`ResolveRoom` generates the reward draft and transitions to the reward phase in one atomic transition.** The room is marked resolved (status `"resolved"`, `resolutionCommitId` set) and then discarded in the same immutable transition; `rewardState` is persisted before the reward screen displays, so a reload returns the same draft.
4. **`SelectReward` applies the reward, advances depth, and materializes the next route in one transition.** This avoids an invalid intermediate state (empty route at depth > 1, which the committed validation rejects). `SelectReward` calls `generateRouteOptions` directly and maps the results, mirroring the existing `materializeRoute` transition. `MaterializeRoute` remains for the initial depth-1 auto-materialize only.
5. **The `invalid-empty-route-depth` persistence rule is KEPT — superseding the prior run's planned relaxation.** The prior (never-dispatched) SESSION-02 ordered a relaxation plus a Controlled Lease Revision 2 adding persistence files; that lease revision was lost with the gitignored `.program/` scratch. Source analysis shows the relaxation was never necessary: the only writer of empty route state is `createInitialRouteState` (depth 1); `SelectReward` populates offers atomically with the depth advance (decision 4), so no legal transition produces an empty route at depth > 1; saves are atomic IndexedDB transactions. The rule stays as a malformed-save guard, and no persistence path enters any lease (CA-06).
6. **Reward application respects build slot limits.** `SelectReward` appends the base reward to `build.activeSkillIds` (max 3) or `build.passiveEquipmentIds` (max 4); full slots reject with `active-skills-full`/`passive-equipment-full`. The generator is already context-aware (slot counts) so drafts usually fit, but the reducer is the authoritative guard.
7. **Recovery is a separate commit from room resolution.** `CommitRecovery` applies the restore amount (clamped to `integrityMax`) and marks `recovery.committed`. `ResolveRoom` advances to the reward phase regardless of whether recovery was committed — the player can decline recovery and still advance.
8. **Shop purchases are individual durable actions.** `BuyShopItem` deducts `runCurrency` by the stored price and adds the itemId to `purchasedItemIds`; re-purchase and insufficient-currency are rejected; the room resolves separately.
9. **Room status transitions `"ready" → "in_progress" → "resolved"`.** `BuyShopItem`/`CommitRecovery` set `"in_progress"`; `ResolveRoom` sets `"resolved"` immediately before discarding the room in the same transition, keeping the zod `resolved ⇔ resolutionCommitId` coherence rule satisfied by construction.
10. **Enhancement effects are tracked but not applied in gameplay.** Enhancement IDs and rolled params live in `RewardCardSnapshot.enhancementIds`/`rolledParams`; gameplay effects are deferred to the combat engine feature. Reward application adds only the base skill/equipment.
11. **The durable record never stores reward `status: "selected"`/`"applied"`.** Selection and application are one atomic transition (decision 4), so `RewardState` persists only `"offered"`. The enum values remain for schema compatibility. The `status: "selected"`/`"applied"` rejections are still implemented for hand-built/legacy states (belt-and-braces).
12. **Bounded e2e currency fixture (restated standing authorization from the prior run's final report).** Runs start with `runCurrency: 0` and no committed mechanic grants currency (combat rooms are deferred), so the shop browser journey seeds currency by rewriting the scalar `runCurrency` on an otherwise committed stored record between app loads; the production parser validates the seeded record on reload. The fixture never invents room/reward state.
13. **Reconciliation of inherited work (Step 1 disposition).** Inspected sources: prior-run FINAL-REPORT.md, STATE.md (prior run), SESSION-01..03 prompts, `.gitignore`, `git log`, and the current source tree at plan HEAD `86e6ee8`. Dispositions: prior-run S01 work = implemented and committed (kept); prior-run S02/S03 = never dispatched (blocked by a runtime spawn-validator seam — an environment failure, not a product defect); prior-run preflight dispositions (e2e fixture authorization, `EffectParam` type-only import authorization, arch M03 note) = preserved, restated in the relevant session prompts; prior-run lease revision for persistence files = superseded by CA-06 (rule kept); the stale git worktree registrations listed by the prior final report still exist under `.program/` (gitignored scratch) — cleanup is an Orchestrator/environment concern, not a session.
